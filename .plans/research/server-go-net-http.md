## 1. Keep-alive decision rule

The decision of whether a connection may be reused lives in three places that must agree: `transfer.go`'s `shouldClose` (parses the request), `server.go`'s `chunkWriter.writeHeader` (decides the response's own `Connection` framing), and `server.go`'s `response.shouldReuseConnection` (the final gate `conn.serve` checks after the handler returns).

- **`shouldClose(major, minor int, header Header, removeCloseHeader bool) bool`** — `transfer.go:756-772`. Rule, in order:
  1. `major < 1` → always close (HTTP/0.9).
  2. HTTP/1.0 (`major==1, minor==0`): close unless the `Connection` header contains the token `keep-alive` (i.e. HTTP/1.0 defaults to close-per-response; keep-alive is opt-in and must be requested by the client).
  3. HTTP/1.1+: close only if `Connection` contains the token `close`; otherwise persistent by default. If `removeCloseHeader` is true (only for outbound writes) the `Connection` header is deleted from the header map after being read.
  - This is called once at request-parse time as `req.Close = shouldClose(req.ProtoMajor, req.ProtoMinor, req.Header, false)` — `request.go:1179` — and again for responses inside `readTransfer` — `transfer.go:510`.
- **HTTP/1.0 keep-alive tracking on the response side**: `response.wants10KeepAlive` is precomputed at `readRequest` time from `req.wantsHttp10KeepAlive()` — `server.go:1116`, `request.go:1540-1545` (true only if proto is exactly 1.0 and `Connection` contains `keep-alive`). `response.wantsClose` is precomputed from `req.wantsClose()` — `server.go:1117`, `request.go:1547-1552` (true if `req.Close` was already set by `shouldClose`, or if `Connection` contains `close` on the *response*-time re-check).
- **Close-delimited body forces close**: in `chunkWriter.writeHeader` (`server.go:1404-1410`): if the request is `< HTTP/1.1` or `wantsClose` is set, `w.closeAfterReply = true`. Separately, if the (already computed) response `Connection` header is `"close"`, or the server has keep-alives globally disabled (`!keepAlivesEnabled`, i.e. `Server.SetKeepAlivesEnabled(false)` was called or the server is shutting down), `closeAfterReply` is also forced true (`server.go:1408-1410`).
- **HTTP/1.0 keep-alive promotion**: if the request wanted 1.0 keep-alive and keep-alives are enabled and the response has an explicit `Content-Length`, the server *adds* `Connection: keep-alive` to the response and clears `closeAfterReply` (`server.go:1387-1394`, and again `1399-1403` sets the header if not already present) — this is the only path where HTTP/1.0 becomes persistent, and it hinges on Content-Length being known (chunked/close-delimited HTTP/1.0 bodies are never kept alive, matching the "close-delimited response forces close" rule).
- **Final gate — `response.shouldReuseConnection()`** (`server.go:1726-1750`), called from `conn.serve` after the handler returns and `finishRequest` has flushed everything (`server.go:2144-2151`): the connection is reused only if *all* of:
  - `!w.closeAfterReply`
  - the handler actually wrote exactly `contentLength` bytes when a `Content-Length` was declared and a body is allowed and the method isn't HEAD (protects against desync from under/over-writes)
  - no earlier write error occurred on the connection (`w.conn.werr == nil`)
  - the request body was not closed early (see §3) — `w.closedRequestBodyEarly()`
  - If all pass, `conn.serve` sets `StateIdle`, arms the idle-timeout read deadline (or clears it), and loops back to `readRequest` for the next message (`server.go:2152-2182`); otherwise it closes the connection (with a lingering close in the two cases noted in §9, otherwise an immediate close via the deferred cleanup in `serve`).
  - A special exception: even if `shouldReuseConnection` would allow reuse, if the server is in the process of shutting down (`!w.conn.server.doKeepAlives()`), `conn.serve` returns immediately after the response instead of reading the next request (`server.go:2155-2161`), with a comment acknowledging the client "might think they can send another request."

## 2. Pipelining policy and response ordering

- **No pipelining support is implemented, by design.** The load-bearing comment sits directly in `conn.serve`, `server.go:2129-2135`. Paraphrased: HTTP cannot have multiple simultaneous active requests on the same connection (footnote: not strictly true, because of pipelining, but they deliberately don't implement it "because it was never deployed in the wild and the answer is HTTP/2"). Consequently the server reads exactly one request, then runs the handler for it synchronously in the same goroutine, then writes its response, and only then reads the next request — `inFlightResponse = w; serverHandler{c.server}.ServeHTTP(w, w.req); ... w.finishRequest()` (`server.go:2136-2144`). This trivially guarantees response ordering matches request order: there is only ever one in-flight response per connection, so no reordering logic is needed or exists.
- **What "pipelining" support does exist is incidental, at the byte level**: `connReader.backgroundRead` (`server.go:745-783`) starts a background 1-byte read on the underlying `net.Conn` once the current request's body has been fully consumed, purely to detect early client disconnects (feeds `CloseNotifier`/context cancellation). If that background read succeeds in reading a byte, the comment at `server.go:748-772` explains this byte is treated as evidence of a pipelined next request already buffered by the client, and — as of Go 1.11 — this event is **not** allowed to fire `CloseNotify` or cancel the request context, specifically because doing so broke real clients (`apt-get`) that pipeline. The byte itself is stashed in `connReader.hasByte`/`byteBuf` and is the first byte handed back to the next `readRequest` call.
- **`chez-httparse`'s close-marked-message-then-error behavior mirrors this design decision exactly**: since Go never attempts to read a second request until the first response is fully written, a "Connection: close"-marked first message followed immediately by a second pipelined request line is a non-issue for Go — it wouldn't even attempt to parse the second message, because `closeAfterReply` sends the connection straight to `conn.close()` after `finishRequest` (`server.go:2146-2150`) without another `readRequest` call. This validates the todo you already wrote in your own notes about httparse's `'error` on data-after-close: not reading further is the correct behavior, and it's exactly what Go's connection loop naturally does by only reading one request at a time.
- **The `CloseNotifier` pipelining caveat** is documented twice: once on the interface itself (`server.go:229-236`, `CloseNotifier.CloseNotify` doc) and once operationally in `connReader.backgroundRead`'s comment (`server.go:748-772`). Interface doc, paraphrased: if using HTTP/1.1 pipelining while processing an idempotent method like GET, the arrival of the next pipelined request can spuriously fire the close-notify channel; this is called out as a known false positive that's tolerable in practice because browsers don't pipeline. This is verified by a dedicated test, `TestCloseNotifierPipelined` (`serve_test.go:3891-3939`): it sends two pipelined `GET` requests over one connection and asserts that `CloseNotify()` does **not** fire while the second, already-buffered request sits waiting — i.e. the Go 1.11 fix (not firing on the background-read byte) is regression-tested.

## 3. Request body streaming to handlers, response body streaming out, and backpressure

**Inbound (request body → handler), all HTTP/1.x, no HTTP/2 in scope:**
- The parsed body is wrapped in a `*body` (`transfer.go:819-832`) whose `src` is one of: `internal.NewChunkedReader(r)` for chunked bodies, `io.LimitReader(r, realLength)` for a known `Content-Length`, or the raw `bufio.Reader` `r` itself for a close-delimited (no length, HTTP/1.0-style) body (`transfer.go:571-591`). The handler reads it via ordinary `io.Reader.Read` calls on `Request.Body` — there is no separate streaming/event API; backpressure is entirely a function of the handler simply not calling `Read` (Go's blocking-Reader model gives you backpressure for free: no thread is spun up to pre-drain the socket into memory).
- **Read-limit enforcement (not a body-size cap, a header-size cap)**: while reading the request line + headers, `connReader.remain` is set to `initialReadLimitSize()` = `maxHeaderBytes() + 4096` "bufio slop" (`server.go:960-962`, `1048`), and every `connReader.Read` call refuses to read past `remain` (`server.go:837-847`, `hitReadLimit`). Once headers are parsed, `c.r.setInfiniteReadLimit()` is called (`server.go:1067`, sets `remain = maxInt64 = 1<<63 - 1`, `http.go:102-104`) — **the body itself is NOT size-limited by the connection layer at all**; an unbounded `Content-Length` or unbounded chunked body will be streamed through with no cap unless the *handler* opts in.
- **Handler opt-in body cap**: `http.MaxBytesReader(w ResponseWriter, r io.ReadCloser, n int64) io.ReadCloser` (`request.go:1209-1214`) wraps the body in a `maxBytesReader` (`request.go:1226-1278`) that returns `*MaxBytesError{Limit: n}` once `n+1` bytes have been requested. Wrapping happens only if the *handler* (or the `http.MaxBytesHandler(h, n)` middleware, `server.go:4286-4292`) chooses to call it — it is not automatic, not configured on `Server`, and the read past the limit does **not** by itself produce a 413 response (see §8: mapping the error to a status is the handler's job). What it *does* do automatically, via a private `requestTooLarger` interface check (`request.go:1259-1271`) matched by `response.requestTooLarge()` (`server.go:566-572`), is: set `w.closeAfterReply = true`, set `w.requestBodyLimitHit = true`, and (if headers haven't been sent yet) set `Connection: close` on the response — i.e. it forces the connection to close after this response regardless of what the handler does with the error, specifically so the server does not try to resync on the next request after abandoning a still-larger body mid-stream.
- **Full-duplex vs. half-duplex default**: by default (`response.fullDuplex == false`), if the handler starts writing a response before it has read the entire request body, `WriteHeader`'s helper (called via `chunkWriter.writeHeader`, `server.go:1447-1474`) will itself drain (discard) up to `maxPostHandlerReadBytes` = `256 << 10` = 262144 bytes (`server.go:1164`) of the remaining body so the connection can still be reused for a following request. If more than that remains unread (`unreadDataSizeLocked() >= maxPostHandlerReadBytes`), it gives up, calls `response.requestTooLarge()` (same helper as MaxBytesReader — forces `Connection: close`), and does not attempt the drain. This draining happens again, unconditionally this time (not capped), in `response.finishRequest` → `w.reqBody.Close()` (`server.go:1717`; `body.Close`, `transfer.go:983-1027`), which is the same `maxPostHandlerReadBytes`-bounded "early close" logic (`transfer.go:999-1019`) — i.e. `finishRequest` also tries to drain a capped amount of leftover body (again to permit reuse) and sets `earlyClose=true` (checked by `shouldReuseConnection`, §1) if it can't.
- A handler can opt out of the half-duplex default with `ResponseController.EnableFullDuplex()` → `response.EnableFullDuplex()` (`server.go:509-512`), which lets it read the body and write the response concurrently; the doc comment explains the historical deadlock reason for the half-duplex default (Issue 15527: clients that fully write their request before reading any response can deadlock against a server that starts writing before it's consumed the body) — `server.go:1433-1446`.

**Outbound (response body → wire):**
- The path is `response.Write` → `response.w` (a pooled `*bufio.Writer`, size `bufferBeforeChunkingSize` = 2048 bytes, `server.go:342`, `1123`) → `chunkWriter.Write` (`server.go:377-400`) → `conn.bufw` (a pooled `*bufio.Writer` of size `4<<10` = 4096 bytes wrapping the raw socket via `checkConnErrorWriter`, `server.go:2036`). `chunkWriter.Write` prefixes each buffered flush with a hex chunk-size line and trailing CRLF when `chunking` is true (set by `chunkWriter.writeHeader`'s framing decision, see §7), and on any write error it immediately does `cw.res.conn.rwc.Close()` — i.e. a write error is fatal to the connection immediately, not deferred to `shouldReuseConnection`.
- **Backpressure out**: this is a synchronous, blocking `io.Writer` chain all the way to the kernel socket buffer (`net.Conn.Write`) — the handler's `Write` call blocks if the OS socket buffer is full and the client isn't draining, i.e. the whole design assumes one handler goroutine per connection and lets TCP flow control do the backpressure job. There is no separate "outstanding bytes" counter and no async write queue (this is the opposite design point from chez-libuv's async, callback-driven `uv_write`, which has no built-in queue depth either per ADR-0018 — but Go's synchronous model sidesteps the problem entirely by blocking the handler goroutine instead of needing a queue-depth signal).
- **`response.ReadFrom`** (`server.go:606-671`) is a `io.ReaderFrom` optimization (used when a handler does `io.Copy(w, someFile)`) that special-cases sendfile/splice-capable underlying connections; it still sniffs/flushes the first `sniffLen` bytes normally first so Content-Type sniffing and header-write ordering are preserved (`server.go:621-631`).
- **Flush semantics**: `Flusher.Flush()` (`server.go:1756-1770`) forces an implicit `WriteHeader(200)` if none was sent, then flushes both buffer layers. Once a flush has happened, the response is irrevocably in "streaming" mode — headers are already on the wire.

| `DefaultMaxHeaderBytes` | **`1 << 20` = 1,048,576 bytes (1 MiB)** | `server.go:936-939` | Cap on header bytes (request line + header block), used when `Server.MaxHeaderBytes <= 0`. |
| `DefaultMaxHeaderValueCount` | **500** | `server.go:941-944` | Cap on number of header *values* (not header lines — comma-joined values on one line count once, repeated header lines count each), used when `Server.MaxHeaderValueCount <= 0`. |

Only the *header* size (1 MiB) and header *value count* (500) have non-zero defaults out of the box.

## 5. `Expect: 100-continue` handling

- Detected via `Request.expectsContinue()` = `hasToken(Header.get("Expect"), "100-continue")` (`request.go:1536-1538`).
- In `conn.serve`, right after a successful `readRequest`, only if the request is HTTP/1.1+ and has a non-zero declared `ContentLength` does the server wrap `req.Body` in an `*expectContinueReader` (`server.go:2104-2116`) and arm `w.canWriteContinue`. If the header says `Expect` but it's not exactly `100-continue`, the server immediately answers `417 Expectation Failed` via `response.sendExpectationFailed()` (`server.go:2113-2115`, `2260-2276`) — sets `Connection: close`, writes the status, and calls `finishRequest()` right there (never invokes the handler). The `417` comment explicitly cites RFC 7231 §5.1.1 ("MAY respond with 417... to indicate that the unexpected expectation cannot be met") — this is optional-per-spec but is what Go does unconditionally.
- The **100 Continue itself is sent lazily, on the handler's first `Body.Read`**, not eagerly on request receipt: `expectContinueReader.Read` (`server.go:994-1009`) checks `canWriteContinue` (an atomic, guarded by `writeContinueMu` against a race with the main response writer also touching headers) and, if still armed, writes the literal status line `HTTP/1.1 100 Continue\r\n\r\n` straight to `conn.bufw` and flushes immediately, then clears the flag before delegating to the real body reader. This means a handler that never reads the body never triggers the 100.
- `response.disableWriteContinue(skipDrain bool)` (`server.go:574-598`) is the single choke point that permanently disarms `canWriteContinue`; it's called from three places: (a) `WriteHeader` itself, any time the handler sends its own final status without having read the body first — `code == 100 || code >= 200` disables it, and for `code >= 200` (a real final answer) it also passes `skipDrain=true`, meaning the server will *not* try to drain the unsent body and instead force `closeAfterReply=true` and mark the `expectContinueReader` closed, because the client was told 100-continue would come but never got it, so it will never send the body — the connection cannot be safely reused (`server.go:1215-1221`, `1412-1431`); (b) the panic-recovery deferred cleanup in `conn.serve` (`server.go:1943-1944`); (c) `finishRequest` as a catch-all (`server.go:1709-1711`).
- No separate timer/deadline governs how long the server will wait between sending 100-continue and the client actually starting to send the body — it is purely reactive to the handler calling `Read`; the connection's normal `ReadTimeout`/`ReadHeaderTimeout` machinery (§4, both unlimited by default) is what would eventually bound this if configured.
- Tests: `TestServerExpect` (`serve_test.go:2168`), `TestIssue13893_Expect100` (`5150`), `TestIssue11549_Expect100` (`5177`), `TestServerReadAfterWriteHeader100Continue` (`7725`), `TestServerReadAfterHandlerDone100Continue` (`7756`), `TestServerReadAfterHandlerAbort100Continue` (`7783`), `TestServerExpect100ContinueUnreadBody` (`7811`), `TestNoSniffExpectRequestBody` (`clientserver_test.go:1574`).

## 6. Upgrade / CONNECT handling

- **There is no built-in generic `Upgrade:` handling and no built-in `CONNECT` tunnel in `net/http`'s HTTP/1.x server path.** Both are left entirely to the application handler via `Hijacker`. Confirmed by grepping `server.go` for `CONNECT` and `Upgrade`/`101`/`StatusSwitchingProtocols`: the only structural special-casing is (a) the `Host`-header-is-mandatory check is waived for `CONNECT` requests and for the literal HTTP/2 upgrade probe (`req.Method != "CONNECT"` exclusion at `server.go:1071`), and (b) `WriteHeader`'s 1xx path explicitly avoids emitting further buffered headers after a `101 Switching Protocols` response (`server.go:1225-1236`, comment: "We shouldn't send any further headers after 101 Switching Protocols"), because at that point the connection semantics belong to whatever protocol was switched to.
- A `CONNECT` request or a WebSocket-style `Connection: Upgrade` request is parsed as an ordinary request (its request-line target is handled specially only in URL-parsing: `justAuthority` logic in `readRequestLimit`, `request.go:1128-1149`, so `CONNECT host:port HTTP/1.1` doesn't get mangled by the normal URL parser), routed to the registered `Handler` like any other request, and it is entirely the handler's job to detect the upgrade/CONNECT intent, respond appropriately (e.g. write `101`/`200` and then), and call `ResponseWriter.(Hijacker).Hijack()` (`server.go:2280-2301`) to take raw ownership of the `net.Conn` + any already-buffered bytes. Once hijacked, `conn.hijackedv` is set and the server's read loop, timeouts, and `finishRequest`/`shouldReuseConnection` machinery all stop touching the connection (checked via `c.hijacked()` at multiple points, e.g. `server.go:1033-1035`, `2140-2143`).
- This is regression-tested end-to-end for WebSocket specifically via `TestH12_WebSocketUpgrade` (`clientserver_test.go:1813-1842`), which sends `Connection: Upgrade` / `Upgrade: WebSocket` and asserts the server still answers as a normal HTTP/1.1 response (`h.Set("Foo","bar")` in the handler, no protocol switch) — proving the stdlib server applies **zero** magic to the Upgrade header by itself; a real WebSocket server built on `net/http` must Hijack.
- The one *real* upgrade the server does implement itself is unencrypted/h2c HTTP/2: `http1ServerSupportsRequest` (`server.go:1127-1142`) special-cases the literal `PRI * HTTP/2.0` preface line, and `maybeServeUnencryptedHTTP2` (`server.go:2226-…`, referenced at `2043-2047`) hands the connection to the HTTP/2 server when `Server.Protocols` enables `UnencryptedHTTP2()`. That path is out of scope for an HTTP/1-only server like ours but is worth knowing it exists so a `PRI * HTTP/2.0` request line isn't misclassified as HTTP/0.x-and-rejected by an HTTP/1-only implementation the way `http1ServerSupportsRequest` deliberately avoids doing (`server.go:1139-1141`: "Reject HTTP/0.x, and all other HTTP/2+ requests" — but with the explicit `PRI * HTTP/2.0` carve-out one line above).
- Legacy TLS-ALPN-based protocol upgrade (`TLSNextProto`) is a separate, TLS-only mechanism (`server.go:2007-2017`) not relevant to a plaintext-first HTTP/1 server.

## 7. Framing precedence (Content-Length vs Transfer-Encoding, duplicates, HEAD, 1xx/204/304)

All of this logic is centralized in two functions, which is itself a design lesson (see §12): `transfer.go`'s `fixLength` (request/response body-length *reading* logic, both request and response paths share it) and `server.go`'s `chunkWriter.writeHeader` (response-*writing* framing logic).

**Reading (`fixLength`, `transfer.go:669-751`, and `parseTransferEncoding`, `transfer.go:638-664`):**
1. `Transfer-Encoding` is parsed first and is deliberately strict: only a single `Transfer-Encoding` header value, and it must be exactly (case-insensitively) `"chunked"` — anything else, or more than one value, is rejected as `*unsupportedTEError` (`transfer.go:651-660`), which the server maps to `501 Not Implemented` (see §8). `Transfer-Encoding` is ignored entirely on HTTP/1.0 requests (`transfer.go:646-649`, citing Go issue 12785).
2. **Duplicate/conflicting `Content-Length` headers are hardened against explicitly** (`transfer.go:673-691`, citing Go issue 16490 and RFC 7230 §3.3.2): if more than one `Content-Length` value is present, they must all be textually identical after trimming, or the request is rejected outright with an error (message: "message cannot contain multiple Content-Length headers"); if they're duplicate-but-equal, they're collapsed to a single value.
3. Body-length-exempt status classes are checked next and return length `0` unconditionally regardless of any header: responses to `HEAD`/other `noResponseBodyExpected` methods (`transfer.go:702-704`, `258-260`, currently only `HEAD`), any 1xx status (`705-707`), and `204`/`304` (`708-711`).
4. **Transfer-Encoding wins over Content-Length**: if chunked was set, any `Content-Length` header is deleted from the header map and length is reported as `-1` (chunked) (`transfer.go:726-729`) — the comment explicitly quotes RFC 9112's rule that Transfer-Encoding overrides Content-Length in this situation and that this ought to be treated as a smuggling-risk error by strict intermediaries, but Go's own server chooses the permissive "accept it after stripping Content-Length" behavior rather than rejecting the message outright.
5. Otherwise, if `Content-Length` is present, that value is used (`transfer.go:732-734`).
6. Otherwise (no framing header at all): for **requests**, length is `0` (no body assumed) (`transfer.go:738-746`); for **responses**, length is `-1`, meaning "read until connection close" (`transfer.go:749-750`) — this is the literal "close-delimited body" case referenced in §1.
7. Special HEAD-response carve-out: even though step 3 zeroes body length for HEAD responses, if the *caller* is reading a `Response` to a `HEAD` request, the `Content-Length` *header value itself* (not the derived body length) is still parsed and stored into `t.ContentLength` for informational purposes (`transfer.go:542-547`) — i.e. Go still tells a client-side caller what Content-Length the server *claimed*, while correctly not expecting any actual body bytes to follow.
8. `bodyAllowedForStatus(status)` (`transfer.go:469-479`) is the single predicate used everywhere for "does this status class carry a body at all": false for all 1xx, 204, and 304; true otherwise. `suppressedHeaders(status)` (`transfer.go:487-496`) says which headers must never appear on a body-less response: `304` suppresses `Content-Type`/`Content-Length`/`Transfer-Encoding` (citing RFC 7232 §4.1), any other body-less status suppresses just `Content-Length`/`Transfer-Encoding`.

**Writing (`chunkWriter.writeHeader`, `server.go:1313-1566`):**
1. If the handler finished without ever setting an explicit `Content-Length` or `Transfer-Encoding`, and the status class allows a body, and either it isn't a HEAD request or some bytes were actually produced, the server auto-computes and sets `Content-Length` from the size of the (already fully buffered, since the handler is done) response — even setting it to literal `0` — specifically to keep HTTP/1.0 keep-alive clients happy (`server.go:1368-1385`).
2. If both an explicit `Content-Length` and a `Transfer-Encoding` other than `identity` are present simultaneously, Go logs a warning and drops the `Content-Length`, letting Transfer-Encoding win (`server.go:1498-1505`) — same precedence direction as the read side.
3. Final framing decision tree (`server.go:1507-1539`), evaluated in this order: **(a)** HEAD request, or body not allowed for this status, or status is exactly `204` → strip any `Transfer-Encoding`, no chunking, (and per step 8 above `Content-Length` is separately suppressed for 204/1xx/HEAD-with-no-explicit-length via `bodyAllowedForStatus`/`suppressedHeaders` on the read side — on the *write* side this is handled by the `!isHEAD || len(p) > 0` guard in step 1 and by `bodyAllowedForStatus` gating the content-type-sniff/suppressed-header block at `server.go:1476-1492`). **(b)** else if an explicit (numeric, valid) `Content-Length` was set → no chunking, `Transfer-Encoding` stripped. **(c)** else if HTTP/1.1+: if the handler explicitly set `Transfer-Encoding: identity`, don't chunk and force `closeAfterReply=true` (length signaled by EOF-on-close — the comment cites this as the setup recommended by the Server-Sent-Events spec §8); otherwise default to `Transfer-Encoding: chunked`. **(d)** else (HTTP/1.0 response, no Content-Length known): cannot chunk, so force `closeAfterReply=true` (close-delimited response, per §1).
4. `Content-Length` and non-`identity` `Transfer-Encoding` are mutually exclusive on the wire: whenever `cw.chunking` ends up true, any `Content-Length` header is deleted right before writing (`server.go:1542-1544`).
5. `Connection` header rewriting happens last (`server.go:1549-1560`): the server only overrides/deletes an existing `Connection` header if `closeAfterReply` is set *and* (keep-alives are disabled globally, or the handler didn't already say `close` itself) *and* this isn't a successful protocol-switch response (101) — in which case, for HTTP/1.1+, it writes `Connection: close` itself.

## 8. Parse/policy/handler error → response mapping, and whether the connection closes

This is entirely driven by the `switch` in `conn.serve` immediately after a failed `readRequest` (`server.go:2063-2101`), plus two special-cased earlier rejections (`417`, `501` for unsupported TE) and the general panic recovery path.

The umbrella takeaway: Go's HTTP/1 server has exactly three *server-generated* status codes for connection-layer failures — 431 (header too big), 501 (bad Transfer-Encoding), and the `statusError`-driven 400/505 family (bad request line/version/Host/headers) — plus 417 for a policy rejection (unsupported Expect) before the handler runs. Everything past that point (body-size limits, malformed chunked bodies, handler panics) is either handled by convention in the handler or simply terminates the connection without a status line at all.

## 9. Close / shutdown protocol (lingering close, FIN, half-close)

- **Ordinary close**: `conn.close()` (`server.go:1789-1793`) = `finalFlush()` (returns the pooled bufio reader/writer, flushing the writer first, `server.go:1772-1787`) then a bare `c.rwc.Close()`. This is what happens on all the error paths above except the two lingering-close cases, and is what happens whenever `shouldReuseConnection()` is false for an ordinary reason (write error, body under-write, early body close) without `requestBodyLimitHit`.
- **Lingering / graceful close — `conn.closeWriteAndWait()`** (`server.go:1814-1847`): calls `finalFlush()`, then, if the underlying conn implements a `CloseWrite() error` method (true for `*net.TCPConn`, asserted at compile time via `var _ closeWriter = (*net.TCPConn)(nil)`, `server.go:1808-1812`), it calls `CloseWrite()` — i.e. sends a TCP **half-close (FIN)** on the write side only, leaving the read side open — and then **sleeps for `rstAvoidanceDelay` (500 ms)** before returning (the caller then does a full `rwc.Close()`). The doc comment (`server.go:1814-1846`) is unusually thorough and worth reading directly (`server.go:1826-1846`): it cites RFC 7230 §6.6's recommendation that a server "continues to read from the connection until it receives a corresponding close by the client, or until the server is reasonably certain that its own TCP stack has received the client's acknowledgement of the packet(s) containing the server's last response," and explains Go deliberately does **not** implement true half-close draining (reading until client-EOF or an ACK signal) because there's no portable way to detect "the client has ACKed my FIN" from user space without low-level socket APIs, and instead approximates "reasonably certain" with a flat time-based sleep. There's an explicit `TODO(bcmills)` noting this delay is hard-coded rather than a configurable `Server` field.
- **Exactly two call sites trigger the lingering close** (verified by grep, both cited in §8's table): the 431 header-too-large path (`server.go:2075`) and the `requestBodyLimitHit`/`closedRequestBodyEarly` path after a normal handler return (`server.go:2148`). Every other non-reuse path (write errors, plain `Connection: close`, HTTP/1.0 without keep-alive, panics, 501/400/505/417) uses the ordinary immediate `c.close()` instead. This is a real design choice worth copying deliberately rather than by accident: the lingering close is reserved specifically for the two cases where the server has decided to hang up *while the client might still be mid-write of a request body the server chose not to fully consume* — i.e. exactly the scenarios where an immediate RST is most likely to also truncate the *response* the server just sent, because the client's kernel may discard unread inbound data (the server's response) when it also sees a hard RST following unacknowledged local writes.
- **`Server.Close()`** (`server.go:3190-3218`): immediate/hard shutdown — closes all listeners, waits for the listener-accept goroutines to exit, then force-closes every connection in `StateNew`/`StateActive`/`StateIdle` via a bare `c.rwc.Close()` (no lingering, no draining). Explicitly documented as not touching hijacked connections at all (`server.go:3194-3196`).
- **`Server.Shutdown(ctx)`** (`server.go:3229-3288`): graceful shutdown — closes listeners immediately, fires any `RegisterOnShutdown` hooks in new goroutines (fire-and-forget, not waited on), then polls `closeIdleConns()` (`server.go:3301-…`, closes only currently-`StateIdle` connections, treating a connection that's been sitting in `StateNew` for more than 5 seconds without completing its first request's headers as idle too — comment cites Issue 22682) on an exponential backoff from 1ms up to `shutdownPollIntervalMax` (500ms) with 10% jitter, until either quiescent (returns the listener-close error) or the passed-in `ctx` is done (returns `ctx.Err()`). Any connection that is actively serving a request when `Shutdown` is called is left alone to finish naturally — `doKeepAlives()` becomes false during shutdown (`server.go:3759-3761`, checks `shuttingDown()`), so `conn.serve`'s post-response check (`server.go:2155-2161`, discussed in §1) makes sure that connection does not get reused for a following request once it does finish, at which point it becomes idle and gets swept up by the same poll loop.

## 10. Application handler API shape

- Single required interface: `Handler` = `ServeHTTP(ResponseWriter, *Request)` (`server.go:89-91`); `HandlerFunc` (`server.go:2330-2337`) is the usual func-adapter. One handler invocation per request, on the same goroutine that read the request and that will write the response and loop back for the next one on that connection (§2) — i.e. concurrency is per-*connection*, not per-request; `net/http.Server` itself spins up one goroutine per accepted connection (not shown in the files read here, but implied throughout `conn.serve`'s design and confirmed by the whole single-active-request-at-a-time model).
- `ResponseWriter` (`server.go:97-162`) is three methods: `Header() Header` (mutate-before-`WriteHeader`; after `WriteHeader`/`Write`, further header mutations are ignored except for 1xx responses and trailer-prefixed keys — documented in-line), `Write([]byte) (int, error)` (implicit `WriteHeader(200)` on first call if none was sent yet; auto Content-Type sniffing and, if the whole body fits before any flush, auto Content-Length — §7), `WriteHeader(int)` (any number of 1xx informational responses followed by at most one final 2xx-5xx; 1xx are flushed immediately and don't clear the header map, the final one does).
- Optional capability interfaces, all detected by the handler doing a runtime type assertion on the `ResponseWriter` it was handed (never guaranteed — HTTP/2 and wrapped `ResponseWriter`s may not implement them): `Flusher` (`Flush()`, `server.go:164-178`), `Hijacker` (`Hijack() (net.Conn, *bufio.ReadWriter, error)`, `server.go:180-208`, hands over the raw connection and any already-buffered-but-unconsumed bytes, and the server washes its hands of the connection entirely from that point), `CloseNotifier` (deprecated in favor of `Request.Context()`, `server.go:210-238`). There's also an unexported-but-documented `ResponseController`-style surface (`response.SetReadDeadline`/`SetWriteDeadline`/`EnableFullDuplex`, `server.go:501-512`) reachable via the stdlib's separate `http.ResponseController` wrapper type (not itself in the files read here) for per-request deadline control and opting into full-duplex streaming (§3).
- Cancellation/deadline propagation to the handler is via `Request.Context()` (a per-request `context.Context` derived from a per-connection context in `readRequest`, `server.go:1089-1090`), canceled on: handler return (`w.cancelCtx()`, `server.go:2139`), a background-read detecting the client went away (`connReader.handleReadErrorLocked` → `cr.conn.cancelCtx()`, `server.go:813-821`), or a panic-recovery cleanup (`server.go:1943`). This is the *documented* replacement for `CloseNotifier`.
- Request body is a plain `io.ReadCloser` (`Request.Body`), response body is written through the plain `Write([]byte)` method — no separate streaming/chunk API is exposed to handlers; chunking vs. content-length framing (§7) is entirely inferred by the server from how/when the handler calls `Write`/`WriteHeader`/`Flush`, which is the single biggest API-shape decision worth calling out: **handlers never choose the wire framing directly** (they can only strongly influence it by setting `Content-Length` or `Transfer-Encoding` headers before the first write, or by calling `Flush()` early to force chunking).

## 12. Concrete lessons for chez-http-server

1. **One request in flight per connection, strictly serialized, by design — don't build a pipelining/reordering layer.** Go's comment at `server.go:2129-2135` is the industry's own reference implementation explicitly declining to support HTTP/1.1 pipelining because "it was never deployed in the wild and the answer is HTTP/2." Given chez-httparse already surfaces the close-marked-message-then-error behavior you measured, the correct fix is exactly Go's structure: never call `parser-feed!` again on a connection after a message with `F-CONNECTION-CLOSE` (or an HTTP/1.0 non-keepalive message) completes — read one request, run the handler, write the whole response, *then* decide whether to read the next request. This sidesteps the httparse quirk entirely rather than working around it.
2. **Ship with no default read/write/idle timeouts, but make setting them trivial and cheap.** Three of Go's four timeout knobs default to `0` (unlimited); only header-size (1 MiB) and header-value-count (500) are capped out of the box. This is a real, working-in-production design choice by the Go team, not an oversight — but it's also a famous footgun (slowloris-class attacks against unconfigured `http.Server`s are a known Go gotcha). Recommendation: default `chez-http-server` similarly to unlimited body/idle timeouts but strongly document (and maybe even warn-log) when it's started without them configured, and definitely keep a header-size cap on by default the way Go does (there is no excuse not to bound header parsing, since chez-httparse already gives you byte-exact control via `parser-feed!`'s consumed-count).
3. **Centralize framing precedence in one pure function, shared by request and response paths.** Go's `fixLength` (`transfer.go:669-751`) is a single, ~80-line, side-effect-light function that both `ReadRequest` and `ReadResponse` funnel through. Given our own Functional-Core/Imperative-Shell mandate, this maps almost directly onto a pure Scheme procedure: `(determine-body-length is-response? status request-method headers chunked?)` returning a tagged value (`'zero`, `'chunked`, `(length . N)`, `'close-delimited`) plus flags for whether to strip Content-Length/Transfer-Encoding — exactly mirroring the precedence order in §7 (TE beats CL; multiple differing CLs are a hard error; 1xx/204/304/HEAD force zero; absent-both means 0 for requests but close-delimited for responses).
4. **Content-Length must reject duplicates that disagree, not just take the first/last.** `transfer.go:673-691`'s explicit smuggling-hardening (reject if 2+ Content-Length values differ; silently dedupe if they're identical) is a concrete, already-battle-tested rule to port verbatim into our own request validation, given uriparse/httparse don't appear to do this themselves (worth confirming against chez-httparse's own header-duplicate policy before assuming a gap).
5. **Transfer-Encoding parsing should be maximally strict, and 501 (not 400) is the right status for a Transfer-Encoding the server doesn't understand.** Go accepts *only* a single header line equal to exactly `"chunked"`; anything else — multiple values, `gzip`, `identity`, a stray space — is `*unsupportedTEError` mapped to `501 Not Implemented`, and Go deliberately does not echo the bad value back into the body (XSS hardening). This is a two-line policy worth copying exactly given chez-httparse presumably parses whatever the byte-machine grammar accepts, leaving the "do we support this transfer-coding" *policy* decision to our connection layer.
6. **Body size limiting is not the parser's or the connection layer's job by default — it's an explicit, composable `MaxBytesReader`-style wrapper the application opts into**, and even then the framework does not auto-emit 413 — the application/handler decides the status code from the sentinel error, while the framework's only automatic side-effect is forcing `Connection: close` after that response. This is worth deliberately choosing to differ from or match: for us, since we don't yet have a routing/handler layer with per-route policy, we may want a server-wide *default* body cap that layers a MaxBytesReader-equivalent automatically with a real 413, while still exposing the same override hook Go does (an explicit reader wrapper a handler can apply with a different limit).
7. **Half-duplex-by-default, with an explicit escape hatch, is the right default for request/response body interleaving**, precisely to avoid the deadlock Go documents at `server.go:1433-1446` (Issue 15527): a client that fully writes its request before reading any response will deadlock against a server that starts writing its response before fully consuming the request body, if both sides' OS socket buffers fill up. Given chez-libuv has no built-in backpressure/write-queue-depth signal (ADR-0018) and our body streaming will be callback-driven rather than blocking-Read-driven, we need our own explicit rule here — likely: don't start writing the response until the request body is fully read *or* the handler has explicitly opted into full-duplex (mirroring `EnableFullDuplex`), with a bounded "drain the rest, but give up past N bytes and force `Connection: close`" fallback matching `maxPostHandlerReadBytes` (256 KiB) for the common case of handlers that ignore the body (e.g. a `GET`-only route accidentally receiving a body).
8. **Reserve the lingering-close (half-close FIN + fixed delay, then hard close) for exactly the two scenarios where the server unilaterally abandoned reading a body the client might still be sending** — header-too-large and body-limit-hit — and use an ordinary immediate close everywhere else. This is a subtle but well-reasoned distinction (`server.go:1826-1846`'s RFC 7230 §6.6 discussion) that's easy to get wrong by either always lingering (wastes a fixed ~500ms-per-close budget under load) or never lingering (truncates your own final response bytes under an adversarial/lossy client). Given libuv's `uv-close!` is async/explicit-only (ADR-0007) and a second close on a closing handle silently drops the callback, our connection layer needs a single, careful owner of "when do we call uv-close!" that implements this same two-path branch — half-close-then-timer-then-close for the abandon-body cases, straight close otherwise. Since chez-libuv doesn't have `uv_try_write`, an explicit half-close in libuv terms means: stop writing new data, let the pending `uv-write!` queue drain via its completion callbacks, then `uv-close!`; a literal TCP-level FIN-only half-close (uv's `uv_shutdown`) is **not** in the chez-libuv v0.5 API surface per your own inventory, so this design point may need a chez-libuv feature request or an accepted downgrade to Go's `rstAvoidanceDelay`-style flat-sleep-then-full-close as a pragmatic substitute.
9. **CloseNotify-style cancellation has a known, regression-tested false-positive with pipelining that we should design around rather than rediscover**: don't let "a further byte arrived on this connection while a request is still being handled" fire your cancellation signal, only let genuine read-errors/EOF do so (`connReader.backgroundRead`'s Go-1.11-era fix, `server.go:745-783`). Since chez-libuv delivers `on-data`/`on-error`/EOF as distinct callbacks already (per your own libuv notes), this maps cleanly: only propagate cancellation from the `on-error`/EOF callback path, never from "more bytes showed up early."
10. **Adopt Go's negative-space findings as explicit design decisions, not oversights**: no 408 (timeout = silent close, not a response), no `ExpectContinueTimeout` on the server side (100-continue is purely reactive to the first body read, no separate timer), no automatic CONNECT/Upgrade protocol handling (100% delegated to a Hijack-equivalent escape hatch). All three are legitimate, defensible choices for a minimal HTTP/1 server and are worth stating explicitly in our own `.plans/decisions/` ADRs (with this file cited) so a future contributor doesn't "fix" what was a deliberate omission.
11. **Test-suite shape to imitate**: build one big table-driven Host-header-validation test mirroring `TestServerValidatesHostHeader`'s ~20 cases (§11) as an early, cheap conformance check once uriparse + httparse are wired into the connection layer; treat `TestUnsupportedTransferEncodingsReturn501`, `TestInvalidChunkedBodies`, and the `TestCloseNotifierPipelined`-equivalent as the three highest-value "we copied a known-tricky interaction correctly" regression tests to port early, since they each encode a subtle, previously-debated (see the Go issue numbers cited throughout: 3595, 11549, 12027, 12785, 14940, 15527, 16490, 22682, 23921, 31753, 36381) real-world bug rather than an obvious case.
