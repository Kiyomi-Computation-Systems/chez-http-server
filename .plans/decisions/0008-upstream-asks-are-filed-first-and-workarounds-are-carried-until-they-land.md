# 0008: Upstream asks are filed and tackled first; the server carries a workaround for each until it lands

Date: 2026-09-19
Status: accepted (user decision, 2026-09-19)
Plan: [the brief](../2026-09-19-chez-http-server-project-brief.md) "Upstream first"

## Context

The gap analyses (research/gap-*.md, each with a citation refuter) found no blocker and twelve additive changes that make the server smaller or safer. Every claim was re-verified against the source before filing.

## Decision

The twelve issues (plus #42, split out of #33 during our review of its fix; uriparse #18, the follow-up filed when #11 landed; uriparse #21, filed at M2.3; uriparse #24, filed for the Host rules; and chez-httparse #47, filed after M2.5 for the `upgrade` field), the milestone each unblocks, and the workaround meanwhile:

## Consequences

- 2026-09-19, later the same day: five of the twelve landed (see the table). chez-httparse's two and chez-libuv's one are on `main` without a tag, so those pins are commits until v0.3.0 / v0.6.0 exist; uriparse's are in the v0.2.0 tag.
- 2026-09-19, night: chez-httparse tagged v0.3.0 (#32, #35) and v0.4.0 (#33, #34, #36, #42); all six of its issues are closed and its pin moves from commit f878068 to the v0.4.0 tag. Nine of the twelve asks (ten of thirteen with #42) have landed. chez-libuv's pin stays at commit 529ea57 until v0.6.0. Verified by four smoke programs recorded in the ledger (`research/spike/smoke-finish.sps`, `smoke-finish-42.sps`, `smoke-v040.sps`, `smoke-upstream.sps`). Open: chez-libuv #19 #20 (planned upstream), uriparse #11 (optimisation); nothing on the v1 path.
- Each workaround is a named site in the server with a comment pointing at the issue and a test that will go red when the upstream change makes it redundant.
- Dependency pins move when an ask lands, one pin per commit, with the fingerprint check the siblings use.
- 2026-09-19, evening: chez-libuv #21 landed (83e0184). #19 and #20 are planned as one threading arc, Stage 1 then Stage 2; chez-libuv's threading spike re-ran the Q1 gate under collect-safe (its T1) and showed that the 1 ms-timer workaround our #19 text proposed does nothing on a bare callback (its T2b). Reconciled here as spike E5d/E5e (the ticker only works when the loop thread's per-tick Scheme path reaches Chez's trap check; chez-libuv's dispatch path does, a bare callback does not) and posted on #19. The conversion costs about 60 ns per callback (spike E5f).
- 2026-09-19, later that night: uriparse tagged v0.3.0 (7fe6688; #11 via PR #15) and its pin moves from v0.2.0 to the tag; all three uriparse issues are closed. The release also states uriparse's first conformance claim, scoped: `uri-parse-validate` is audited recognizer-equivalent to RFC 3986 Appendix A per mode (recognition only, not error code or offset; `uri-parse` stays lenient by design; its decisions 0028, 0030, 0031), which is the oracle M2's request-target validation cites. The reset reaches only the streaming interface, since validation is not exported over a parse result, so M2's validated forms still allocate per request and the workaround stands there; filed as uriparse #18 (`uri-parse-result-validate`, additive). Eleven of the fourteen filed asks have landed. Open: chez-libuv #19 #20, both planned upstream and needed only by a future worker pool, and uriparse #18, an optimisation; nothing on the v1 path. Verified by `research/spike/smoke-uriparse-v030.sps`, recorded in the ledger.
- 2026-09-19, night, later: chez-libuv tagged v0.6.0 (ad4c1e9; PRs #22, #23, #25, #26): all four chez-libuv asks landed, #19 and #20 the same night they were planned, and its pin moves from commit 529ea57 to the tag. Every dependency is now pinned at a release tag. Thirteen of the fourteen filed asks have landed; open: uriparse #18, an optimisation (closed later the same night; next bullet). Verified by `research/spike/e5g-gc-stall-at-v060.sps`, `smoke-v060-async.sps`, `smoke-v060-tcp.sps` and the E5b re-run, recorded in the ledger.
- 2026-09-19, night, last: uriparse tagged v0.4.0 (611b04b; #18 via PR #19): `uri-parse-result-validate`, and its pin moves from v0.3.0 to the tag. All fourteen filed asks have landed; nothing is open upstream. The one allocation v1 still accepts is CONNECT's `uri-parse-authority-form-validate`, which has no collector path and parses fresh; no ask filed, CONNECT is rare. Verified by `research/spike/smoke-uriparse-v040.sps`, recorded in the ledger.
- 2026-09-24, M2.3: uriparse #21 filed on the owner's word. The request is `validate-component` over a range. The server judges an origin-form target as RFC 9112 §3.2.1 writes it, `absolute-path [ "?" query ]`: it splits at the first `?` and judges both parts with `(uri charset)`. It does not use the collector route design §7.5 planned, for two measured reasons (`research/spike/m2.3-target-alloc.sps`, Darwin arm64). That route reads a leading `//` as an authority, which refuses the valid target `//a@b:c/d`. And it costs 1,232 B per request on the CPS workload, putting the cycle at 3,856 B against the 3,072 B ratchet. The judging route costs 16 B. The copy the whole-bytevector validator needs is the carried workaround. Absolute-form and CONNECT targets keep uriparse's parse-and-validate (0002's amendment of 2026-09-24).
- 2026-09-24, evening: uriparse tagged v0.5.0 (4d95118; #21 via PR #22, release PR #23): `validate-component` over a range, and its pin moves from v0.4.0 to the tag. All fifteen filed asks have landed; nothing is open upstream. Verified by `research/spike/smoke-uriparse-v050.sps`, recorded in the ledger: the ranged verdict equals the verdict on a copy, and the ranged call allocates nothing where the copy cost 16, 80 and 512 B for 2-, 46- and 500-byte targets. No check went red when the pin moved, although the rule above asks for one: the #21 copy's allocation check held the copy's cost, which moving the pin does not change. A probe would have met the rule: a check that the pinned uriparse refuses a ranged `validate-component` goes red at the pin that adds one. A workaround for a missing capability carries such a probe. The carried copy went in the commit after the pin's, by hand: origin-form targets are judged in place. Two copies remain on a target's path, both accepted without an ask: CONNECT's, ahead of a fresh parse that costs far more (design §7.5), and the redirect's, on a refusal path that closes the connection, since `pct-encode` takes a whole bytevector.
- 2026-09-25: uriparse #24 filed on the owner's word, when the owner decided RFC 9112 §3.2's Host rules. A Host value is `uri-host [ ":" port ]`, and every request carries one, so judging it through a copy would cost 16 to 64 B per request, growing with the value. The owner chose to wait rather than carry that copy. uriparse tagged v0.6.0 the same day (40d645f; #24 via PR #25, release PR #26), and the pin moves from v0.5.0 to the tag. All sixteen filed asks have landed; nothing is open upstream. Verified by `research/spike/smoke-uriparse-v060.sps`, recorded in the ledger: the ranged verdict and host bounds equal a copy's for eleven Host values inside a header line, an `@` past a value's end splits nothing, and the ranged calls allocate nothing where a copy cost 16, 32 and 64 B for 1-, 16- and 41-byte values. No workaround was carried, so no probe was owed. The Host rules went in the commit after the pin's, judging the value in place.
- 2026-09-25, after M2.5 merged: chez-httparse #47 filed on the owner's word. M2.5 had transcribed llhttp's upgrade rule as `request-upgrades?`, because the parser's own `upgrade` field, which decides the hand-off, was not in `docs/api.org`'s field list. The ask was for documentation only: the parser already stores llhttp's answer and `parser-field-ref` reads it, as llhttp's own `llhttp_get_upgrade` does, so no procedure was asked for. chez-httparse tagged v0.4.1 the same day (9bc669c; #47 via PR #48, release PR #49), with a test lane and no parser change, and its pin moves to the tag. Verified by `research/spike/smoke-httparse-v041.sps`, recorded in the ledger: at every on-headers-complete over the 135 strict fixtures, whole and a byte at a time, the field equals llhttp's rule, and it is 1 in exactly the nine fixtures whose logs pause for an upgrade. All seventeen filed asks have landed; nothing is open upstream.
