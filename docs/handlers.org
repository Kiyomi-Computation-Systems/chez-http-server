#+TITLE: Handlers: answering requests

A handler is a procedure. The server calls it with each request, and sends
back the response it returns.

#+begin_src scheme
(import (rnrs) (http-server))

(serve
 (lambda (request)
   (make-response 200 #f '()
                  (string->utf8 (string-append "You asked for " (request-path request) "\n")))))
#+end_src

~serve~ listens on ~127.0.0.1:8080~ unless ~CHEZ_HTTP_HOST~ and ~CHEZ_HTTP_PORT~ say
otherwise (see [[file:configuration.org][configuration.org]]), and runs until the process gets
~SIGTERM~ or ~SIGINT~ (Ctrl-C). Then it finishes the requests in flight and
returns ([[file:connections.org][connections.org]]). It writes one line to standard output for each
thing that happens, starting with ~listening 127.0.0.1 8080~.

Once ~serve~ has returned, Ctrl-C ends the process at once, so in a REPL it
ends Chez too.

* Reading the request

For ~GET /a/b?x=1~ with ~Host: example.com~:

| Call                        | Gives                                          | Here            |
|-----------------------------+------------------------------------------------+-----------------|
| ~(request-method r)~        | the method, a symbol                           | ~GET~           |
| ~(request-path r)~          | the path                                       | ~"/a/b"~        |
| ~(request-query r)~         | what follows the first ~?~, or ~#f~ with no ~?~ | ~"x=1"~         |
| ~(request-header r "host")~ | the first header with that name, or ~#f~       | ~"example.com"~ |
| ~(request-host r)~          | the site the request is for                    | ~"example.com"~ |

- Header names match in any case: ~"content-type"~ finds ~Content-Type~.
- The spaces around a header's value are not part of it.
- Nothing is decoded: ~/a%20b~ reads ~"/a%20b"~. Decode it yourself if you need to.
- Each byte is one character (Latin-1), so every byte reads back as it was sent.
- A proxy names the site in the target itself: ~GET http://example.com/a~. Then the
  path is ~"/a"~ and the host is ~"example.com"~, whatever the ~Host~ line says
  (RFC 9112). An empty path, as in ~GET http://example.com~, reads ~"/"~.
- ~OPTIONS *~ has the path ~"*"~, and ~CONNECT example.com:443~ the path ~""~.
- With an empty ~Host:~, or none (HTTP/1.0), the host is ~""~.

Each call makes its string when you ask, so a handler pays only for what it reads.

* Reading the body

A request with a body, one with a ~Content-Length~ above 0 or
~Transfer-Encoding: chunked~, reaches your handler as soon as its headers are
in, before its body. To read the body, answer with a reader instead of a
response:

#+begin_src scheme
;; the whole body, as one bytevector
(serve
 (lambda (request)
   (read-whole-body
    (lambda (body) (make-response 200 #f '() body)))))

;; the body piece by piece, as it arrives
(serve
 (lambda (request)
   (let ((n 0))
     (read-body
      (lambda (bv start end) (set! n (+ n (- end start))))
      (lambda () (make-response 200 #f '() (string->utf8 (number->string n))))))))
#+end_src

- ~read-whole-body~ keeps the body in memory, up to 1 MiB. A bigger body gets
  ~413 Content Too Large~. A second argument sets another cap:
  ~(read-whole-body proc 65536)~.
- ~read-body~ calls its first procedure with each piece of the body, the bytes
  ~bv[start, end)~, as the piece arrives. Once the body has ended it calls the
  second, which returns the response.
- ~read-body~ never holds the body whole, so a body of any size streams
  through: a 16 MiB upload added under 100 KB to the server's memory.
- A piece shares memory with the read it arrived in. Copy what you keep.
- A request with no body gets its end at once, so a handler can answer every
  request with a reader.
- Answer with a response instead, and the server sends it at once, without
  reading the body, and closes the connection after it.
- A client can send ~Expect: 100-continue~ and wait to be asked for a big
  body (curl does, for uploads over 1 MiB). Answering with a reader sends
  it ~100 Continue~, and then it sends the body. Answering with a response
  sends no ~100~, so the client never has to send the body at all.
- Fields sent after a chunked body (trailers) are not part of the request:
  the server reads them and drops them.
- If a reader raises, the client gets ~500 Internal Server Error~.

* Keep strings, not the request

A request holds on to the bytes it arrived in, up to ~CHEZ_HTTP_READ_BUFFER_SIZE~
(16 KiB). To keep something for later, keep the strings you read, not the request:
a request you keep keeps its bytes too.

* Answering

~(make-response status reason headers body)~:

- ~status~: a number from 200 to 599;
- ~reason~: a bytevector, such as ~(string->utf8 "OK")~, or ~#f~ for the usual one;
- ~headers~: a list of ~(name . value)~ pairs of bytevectors;
- ~body~: a bytevector, ~#f~ for none, or a producer (below).

What the server adds for you, and what it will not send, is in [[file:responses.org][responses.org]]. If
your handler raises, the client gets ~500 Internal Server Error~ and the server logs
~handler-failed~.

* Streaming a response

When you do not know the body's length before you start, give a producer as
the body: a procedure of no arguments that returns the next piece, a
bytevector, and the eof object when there is no more.

#+begin_src scheme
;; five lines, a piece each
(serve
 (lambda (request)
   (let ((n 0))
     (make-response 200 #f '()
                    (lambda ()
                      (set! n (+ n 1))
                      (if (> n 5)
                          (eof-object)
                          (string->utf8 (string-append "line " (number->string n) "\n"))))))))
#+end_src

~(lambda () (get-bytevector-some port))~ streams a file's binary input port.

- An HTTP/1.1 client gets the body chunked, and the connection stays open. An
  HTTP/1.0 client gets it with no length, and the connection closes after it:
  the close is how the client knows the body has ended.
- The server calls the producer only while the client keeps up. Once more than
  256 KiB (~CHEZ_HTTP_WRITE_HIGH_WATER~), or 64 pieces, are written and not
  yet taken by the client, it waits until no more than 64 KiB
  (~CHEZ_HTTP_WRITE_LOW_WATER~) and 16 pieces are. So a slow client costs the
  server little more than 256 KiB and one piece.
- The server gathers pieces of up to 4,088 bytes (4 KiB less the chunk
  framing) into one write, so small rows cost it little. Each piece still
  costs a call and its framing, so return pieces of a few KiB where you can:
  100-byte rows gathered into 16 KiB pieces streamed about 4.7 times faster
  than the rows one at a time (measured on Linux).
- A producer must answer at once: while it runs, the server serves no other
  connection. Stream what is ready, such as a file. A pipe or a socket can
  make it wait for data. Never return an empty bytevector: it counts as a
  failure, like any answer that is not a piece.
- The server calls the producer up to 64 times in a row and sends those
  pieces together, so a producer slow to make each piece delays its own
  pieces too.
- You may return the same bytevector each time: the server copies a piece as
  soon as it takes it.
- The headers go out before the producer is first called. If the producer
  raises, or returns what is not a bytevector with bytes in it or the eof
  object, it is too late for a ~500~: the server closes the connection at once
  and logs ~handler-failed~, naming what came back by its kind and length,
  such as ~(string 5)~, never its value. An HTTP/1.1 client sees the body cut
  short. An HTTP/1.0 client cannot tell a cut-short body from a whole one.
- A ~HEAD~ request, a ~204~ or a ~304~ has no body, so the producer is never
  called. And the server stops calling it early when the client leaves, a
  write times out, or it fails. So don't count on reaching the eof object to
  close what the producer reads. Open a port inside the producer, on its first
  call, and a ~HEAD~ never opens it. A port left open is closed when Chez
  collects it, which can be long after.
- A reader's response can be streamed too.

* Waiting

A handler that has to wait, say for another request, answers ~(awaiting thunk)~
instead. The server runs ~thunk~ on its own, and what ~thunk~ returns is the
answer: a response or a reader. There it can wait with ~await~.

#+begin_src scheme
;; GET /wait waits until a POST arrives, then answers with the POST's body
(define waiting '())

(serve
 (lambda (request)
   (if (string=? (request-path request) "/wait")
       (awaiting
        (lambda ()
          (make-response 200 #f '()
                         (await (lambda (resume) (set! waiting (cons resume waiting)))))))
       (read-whole-body
        (lambda (body)
          (for-each (lambda (resume) (resume body)) waiting)
          (set! waiting '())
          (make-response 200 #f '() (string->utf8 "woke them\n")))))))
#+end_src

- ~(await register)~ calls ~register~ with ~resume~, then waits until something
  calls ~resume~, and gives back what ~resume~ was called with.
- Call ~resume~ once. A second call wakes nothing, and the server logs
  ~late-resume await~.
- Only a handler that answered ~awaiting~ can wait, and so can the reader or
  the producer it answers with. A wait anywhere else fails the handler: the
  client gets ~500~, and the server logs ~handler-failed~.
- While a handler waits, the server reads nothing more from its connection,
  so the next request on it waits too. Other connections go on.
- A waiting handler holds about 3.6 KB until its wait ends, even if its
  client has gone: the server only notices a client leave when it reads or
  writes. Once it has answered, its connection holds no more than any other.

To wait for a time, or to stop waiting after one:

- ~(sleep-ms n)~ waits ~n~ milliseconds: a 10 ms sleep took 10 to 14 ms.
- ~(with-deadline ms thunk)~ runs ~thunk~ and gives back what it returns. Once
  ~ms~ milliseconds have passed, the wait ~thunk~ is in raises
  ~&deadline-passed~, and so does every wait inside it after that.
  ~deadline-passed?~ tells you it was the deadline. Code that is not waiting
  is never cut short.

#+begin_src scheme
;; answer 504 if no POST comes within 30 seconds
(awaiting
 (lambda ()
   (guard (e ((deadline-passed? e) (make-response 504 #f '() #f)))
     (with-deadline 30000
       (lambda ()
         (make-response 200 #f '()
                        (await (lambda (resume) (set! waiting (cons resume waiting))))))))))
#+end_src

- A ~resume~ called after its deadline wakes nothing, and the server logs
  ~late-resume await~, as for a second call.

To look up a host's addresses:

- ~(resolve host)~ waits for the system's resolver and gives back the
  addresses as strings: ~("::1" "127.0.0.1")~ for ~"localhost"~, about 0.2 ms.
- A name that does not resolve raises ~&resolve-error~ (check with
  ~resolve-error?~). ~(resolve-error-reason e)~ says why: ~EAI_NONAME~ for a
  name no one knows, or ~invalid-name~ for one that cannot be asked about:
  empty, too long, or with a NUL in it.
- A lookup a deadline ends is cancelled if it has not begun. One already
  under way still answers later, and the server logs ~late-resume resolve~.

Inside a handler that waits, ~guard~ costs about 3.7 KB each time it runs.
~with-exception-handler~ costs next to nothing.

* Taking an upgrade

A client can ask to switch the connection to another protocol, a WebSocket
say. A handler takes it by answering ~(switch-protocols headers take-over)~.
The server writes ~101 Switching Protocols~ with your headers, then calls
~(take-over t retained)~. From then on the connection is a stream of bytes,
and ~t~, the transport, is how you use it.

#+begin_src scheme
;; a client asking for Upgrade: echo gets back every byte it sends
(serve
 (lambda (request)
   (if (equal? (request-header request "upgrade") "echo")
       (switch-protocols
        (list (cons (string->utf8 "Upgrade") (string->utf8 "echo")))
        (lambda (t retained)
          (when (> (bytevector-length retained) 0) (transport-write! t retained))
          (transport-read-start! t
                                 (lambda (bv start end) (transport-write! t bv start end))
                                 (lambda (why) (transport-close! t)))
          (transport-on-drain! t (lambda () (transport-close! t)))))
       (make-response 200 #f '() (string->utf8 "ask for Upgrade: echo\n")))))
#+end_src

Which requests can be taken:

- An HTTP/1.1 request with ~Connection: upgrade~ and ~Upgrade~, and no body.
  A switch answered to any other request gets ~500~, and the server logs
  ~invalid-response not-an-upgrade~.
- Your ~Upgrade~ header must name a protocol the client's did, or the client
  gets ~500~ (~invalid-upgrade~). The server writes ~Connection: upgrade~
  itself; leave out ~Content-Length~ and ~Transfer-Encoding~. A client that
  also sent ~Expect: 100-continue~ gets ~100 Continue~ first.
- ~retained~ is what the client sent after its request that the server had
  already read. It is usually empty: a WebSocket client waits for the ~101~.

What the transport does:

| Call                                  | Does                                                           |
|---------------------------------------+----------------------------------------------------------------|
| ~(transport-write! t bv [start end] [done])~ | sends the bytes; ~done~ gets ~#f~ once sent, or the error |
| ~(transport-read-start! t on-bytes on-end)~ | each read as ~(on-bytes bv start end)~; ~(on-end why)~ once: ~eof~ or the error |
| ~(transport-read-stop! t)~            | stops reading                                                  |
| ~(transport-close! t)~                | closes, once your writes have gone out                         |
| ~(transport-deadline! t ms proc)~     | calls ~proc~ once ~ms~ milliseconds pass; ~(transport-deadline! t #f)~ cancels |
| ~(transport-on-drain! t proc)~        | calls ~proc~ when the server shuts down                        |
| ~(transport-on-close! t proc)~        | calls ~proc~ once the stream has closed, whoever closed it (at once if it has) |

- Each read's bytevector is yours to keep. A write of no bytes is refused.
- Nothing bounds what you write but you. A client that stops reading leaves
  your writes waiting, in memory. Count what you have written and not yet
  had ~done~ for; past a bound you choose, stop writing, or stop reading what
  you would echo; and arm a deadline to close a client that never catches up.
- Each ~transport-write!~ is a write of its own: the server does not join
  small ones together, as it does for a response. Many small writes are
  slower than one, so join small pieces into one bytevector first.
- A write after ~transport-close!~ is not sent: its ~done~ gets ~ECANCELED~.
  That ~done~, and the one for a write refused as you ask for it, comes on
  the server's next turn, or, if the server stops first, before ~serve~
  returns. A write you ask for in a ~done~ that comes then gets no ~done~.
- One deadline at a time: a new one replaces the last. It is checked every
  ~CHEZ_HTTP_TICK_MS~ (250 ms), so it can pass up to that late.
- When the server shuts down, your drain call is your chance to say goodbye
  (a WebSocket sends close code 1001) and close. The server waits for the
  close, and after ~CHEZ_HTTP_DRAIN_TIMEOUT~ closes the stream itself. The
  drain call runs once; registered while the server is already shutting
  down, it runs at once.
- A taken stream still counts toward ~CHEZ_HTTP_MAX_CONNECTIONS~. One you
  neither read nor time out stays open, a client gone or not, until the
  server shuts down: read it, or arm a deadline.
- Your code runs inside the server's own callbacks, so keep it quick, and it
  cannot ~await~. If it raises, the server logs ~taker-failed~ and closes the
  stream.
- To test your taker without a server, make a transport of your own:
  ~make-transport~ takes the seven procedures the calls above end up in, in
  that order.

* When the server will not start

A malformed setting, such as ~CHEZ_HTTP_PORT=http~ or a ~CHEZ_HTTP_HOST~ that is not
an IP address, stops ~serve~ before it listens. It raises an
~&http-server-config-error~ that names the variable; ~http-server-config-error?~
checks for one.
